# libs/db

Database schema (Liquibase) and the generated, **committed** jOOQ classes for MariaDB.

## Layout

- `src/main/resources/db/changelog/db.changelog-master.yaml` includes `v1/NNN-*.yaml` changelogs. Changelog tables are named `ec_databasechangelog` / `ec_databasechangeloglock` (same in the app config and here).
- `src/main/jooq/...` is the generated code (`com.heldertheking.exochat.db.schema`). It is a source dir, so normal builds never need a database.

## Changing the schema

1. `docker compose up -d` (MariaDB on `localhost:3308`).
2. **Pre-release (nothing deployed): edit the baseline `v1/001-initial-schema.yaml` in place** and wipe the local databases (`docker compose down -v && docker compose up -d`) instead of adding migrations. **Once a database must be kept:** add a new changelog `db/changelog/v1/00N-<what>.yaml`, include it in the master file and never edit an applied changeset.
3. `./gradlew :libs:db:jooqCodegen`. It first runs Liquibase `update` against the dev DB, then regenerates `src/main/jooq`.
4. Commit the changelog and the generated code together.

The connection comes from `JDBC_URL`, `JDBC_USER`, `JDBC_PASSWORD` (defaults match docker-compose: `jdbc:mariadb://localhost:3308/exochat`, `exochat` / `exoch4t`). Code is generated into the default schema so SQL is unqualified and also works against `exochat_test`. `tinyint(1)` becomes `BOOLEAN`; jSpecify nullability annotations are generated.

## Gotchas

- Liquibase and the MariaDB driver are also on the `buildscript` classpath (the plugin needs them at apply time). Keep those versions in sync with `gradle/libs.versions.toml`.
- Primary keys are native `UUID` columns holding UUIDv7 generated by the application (`UuidV7.next()` in `libs/api`); jOOQ maps them to `java.util.UUID`. Never use `UUID()`/`UUID_v4` defaults in the database, they are not time-ordered.
- Tables so far (identity): `user` (login identity: unique `email`, optional unique `phone_number`, `password_hash`), `account` (public persona, globally unique `username`, `standing` MEMBER / RESTRICTED / SUSPENDED, FK to `user`), `account_rule` (platform ALLOW / DENY per account and rule, ADR-013) `session` (one per device: refresh token hashes, active account, expiry) and `relationship` (owner and target account, `type` FRIEND / PENDING_INCOMING / PENDING_OUTGOING / BLOCKED, unique per owner and target, no self links). Deleting a user cascades to its accounts and their relationships. Presence (`AccountStatus`) is not stored.
- Every table has `create_time` and `update_time` (`DATETIME(6)`, the latter maintained by the database).
- A friendship is stored as two `relationship` rows, one per account, a block as one row on the blocking side.
